## 3. Bug real encontrado e corrigido nesta revisão

**`bandit` com 2 achados medium (B104, bind `0.0.0.0`) que eu vinha tratando
como "aceitos" sem nunca checar o código de saída.** `MCP_HOST`/`API_HOST`
em `src/core/settings/config.py` — bind intencional (interface do
container, a porta só é exposta ao host via o mapeamento do compose, que
já restringe a `127.0.0.1`), mas sem `# nosec` documentado. `bandit` sem
`--exit-zero` sai com código 1 para qualquer achado, mesmo medium — isso só
apareceu porque o workflow de CI que acabei de criar (§5) rodou de
verdade e falhou, nas duas branches. Corrigido com `# nosec B104` +
comentário explicando a razão. Commit `1c75d77`.

**Por que isso importa mais do que parece:** ao longo de toda a sessão eu
rodei `bandit` manualmente várias vezes e só li o resumo ("Medium: 2") —
nunca testei se o comando *falharia* num pipeline real. A diferença entre
"ler o relatório" e "verificar o código de saída" é exatamente o que um CI
de verdade cobra e uma leitura manual não.

## 4. CI/CD — por que foi implementado e o que ele cobre

Pedido explícito: avaliar se fazia sentido CI/CD aqui, dado que o repo é
novo. **Resposta: sim, sem ressalvas.**

- A suíte inteira (164 testes) roda sobre **mocks** — nenhum teste toca
  Postgres, RabbitMQ, Ollama ou faster-whisper de verdade. Não precisa de
  GPU nem de runner self-hosted, ao contrário do video-factory (que
  precisa renderizar vídeo de verdade numa GPU).
- `.github/workflows/ci.yml`: `ruff check`, `ruff format --check`,
  `pyright` (strict), `bandit`, `pip-audit`, `pytest`. Roda em push/PR
  para `main` e `dev`, num runner `ubuntu-latest` comum.
- São os **mesmos checks que o `pre-commit` já roda localmente** — a
  diferença é que agora rodam antes de qualquer merge, não dependem de
  ninguém ter instalado o hook na própria máquina.
- **Prova de que funciona**: a primeira execução **falhou** (o bug da §3)
  — não é teatro verde, pegou um problema real na primeira tentativa.

**Não implementado, por decisão consciente:** workflow de docs (mkdocs) —
não há site de documentação ainda, só o README. Avaliar quando/se o
projeto crescer a esse ponto.

- `main`: protegida, estável.
- `dev`: branch de integração, criada a partir de `main` no momento da
  publicação. Trabalho novo deveria ir para `dev` (ou `feature/*` a partir
  de `dev`), com PR para `main` quando estabilizar.
- Ambas publicadas no GitHub (`leonardodg/insta_kb`), CI roda nas duas.
- **Estado agora**: `main` e `dev` estão no mesmo commit (`1c75d77`) — é o
  ponto de partida correto para o fluxo gitflow começar a valer dali.

## 6. Pendências que restam

1. **Subir o `ig-worker` de verdade.** `ig_queue_status` reporta `ig.saved`
   vazia, **0 consumidores** — o código está migrado, testado, mas nenhum
   processo está consumindo a fila agora. É a pendência mais visível do
   projeto.
2. **Testar a API REST contra um servidor rodando de verdade** (não só
   `TestClient`) — nunca subiu via `uvicorn` de fato nesta sessão para um
   teste manual com `curl`/Swagger UI abertos no navegador.
3. **Security review formal** — as checagens automatizadas (bandit,
   pip-audit, segredos no histórico git) estão limpas e foram conferidas
   nesta revisão (§7), mas falta uma passada dedicada (threat model da
   API exposta, revisão da superfície `IG_SESSIONID`/`DATABASE_URL` em
   trânsito, etc.).
4. **Code review final formal** — não rodado.
5. **Proteção de branch no GitHub** (`main` exigindo PR + CI verde antes de
   merge) — mencionado como intenção do gitflow, mas a configuração da
   regra de proteção em si (Settings → Branches) não foi feita nesta
   sessão; é uma ação de configuração no GitHub, não uma mudança de código.
6. **Publicar/divulgar o repo** — está público, mas nenhuma ação de
   divulgação (não que fosse pedida).

## 7. Segurança — o que foi conferido nesta revisão

- `git log --all -p`: nenhum segredo real commitado (`IG_SESSIONID` sempre
  vazio no histórico; senhas são sempre `kb:kb`/`guest:guest` — defaults de
  desenvolvimento documentados no próprio `.env-example`, não credenciais
  reais).
- `.env` fora do git (`.gitignore` confirmado), assim como `downloads/`,
  `output/` e os backups `*_empty_devcontainer_bak/` dos volumes antigos.
- `pip-audit`: limpo agora. Durante a sessão apareceram CVEs reais em
  `urllib3`/`virtualenv` (dependências transitivas do `pre-commit`, não do
  app) — resolvidas com `uv lock --upgrade-package urllib3 --upgrade-package
  virtualenv`, sem tocar em nada do runtime.
- `bandit`: limpo, com as duas exceções documentadas (§3), não silenciosas.
- Isso **não substitui** o item 3 da seção 6 (security review formal).

## 8. Conclusão

O projeto saiu de "stub com `Hello from app!`" para um sistema real,
testado, publicado, com CI pegando bugs de verdade na primeira execução —
exatamente o padrão que foi pedido ("gosto de coisa bem feita"). A maior
lacuna que resta não é de qualidade de código, é de **operação**: o
worker que deveria estar consumindo a fila do Instagram ainda não foi
colocado para rodar.
